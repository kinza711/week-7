# ADR-001: Cursor Pagination for the Task List Endpoint

**Status:** Accepted
**Date:** 2026-09-04
**Deciders:** Kinza Shahzadi (CMIT Internship, Week 7)

## Why this is a real decision

Both offset and cursor pagination are legitimate, widely-used choices for a list endpoint — this isn't a case where one option is obviously wrong. Offset pagination (`page`/`pageSize`) is simpler, lets a client jump straight to an arbitrary page, and is what the rest of this API already uses for `projects`, `project members`, `tags`, and `comments`. A competent engineer could reasonably default to it everywhere, including tasks, for consistency alone. The case for cursor pagination only wins once you weigh it against this specific endpoint's access pattern — which is exactly what this record exists to write down.

## Context

- The task list (`GET /projects/:id/tasks`) is requested on nearly every page load in the UI — it is the single hottest read in the domain, far more frequent than any other list endpoint.
- Tasks are inserted into and updated within a project at a high rate relative to other resources (`tags`, `comments`) — an active team can create or reorder several tasks per minute.
- Every other list endpoint in this domain (`projects`, `project members`, `tags`, `comments`) is comparatively low-churn: rows are added rarely relative to how often the list is read.
- The current frontend design uses a scrolling/"load more" task list, not a numbered page-jump control.
- Client is a single first-party frontend for Phase 4 — there is no third-party API consumer today with a hard requirement to deep-link to "page 40."
- Postgres `OFFSET` cost grows linearly with page depth, which matters more for a frequently-paged, frequently-mutated table than for the domain's other, calmer lists.

## Options Considered

**1. Offset pagination (`page`/`pageSize`), consistent with every other list endpoint**
- *Advantage:* Simplicity and consistency — one pagination style across the whole API, and it supports jumping to an arbitrary page number, which a reporting or admin view might eventually want.
- *Disadvantage:* Under concurrent inserts, a row's page position shifts between requests — the same task can appear twice across two page loads, or be skipped entirely, which is a correctness problem on a list this frequently mutated.

**2. Cursor pagination (opaque cursor, no page number)**
- *Advantage:* Stable results under concurrent inserts — a cursor anchors to a specific row, not a position, so rows already delivered don't shift, duplicate, or vanish across requests.
- *Disadvantage:* No "jump to page N"; the client can only page forward from where it is, which the current infinite-scroll UI doesn't need but a future admin/reporting view might.

**3. Change nothing — offset everywhere, accept the instability on tasks**
- *Advantage:* Zero additional design or implementation cost; this is functionally Option 1 applied without exception.
- *Disadvantage:* Same correctness problem as Option 1, on the endpoint where it's most likely to actually be hit by a real user, given how often tasks change.

## Decision

Use **cursor pagination for the task list endpoint only**; every other list endpoint keeps offset pagination. The cursor payload encodes the row's sort value together with `tasks.id` as a deterministic tie-breaker (`{sortValue, id}`, base64-encoded), so two tasks sharing an identical sort value (e.g. the same `priority` or the same `createdAt` millisecond) still produce a stable, gap-free order instead of a cursor that could duplicate or skip one of them.

**Criterion:** task lists are the one endpoint in this domain where read frequency and write frequency are both high at the same time. Every other list is either read-heavy-but-static (`tags`) or low-traffic (`project members`). Where both pressures coincide, correctness under concurrency was weighted above the convenience of numbered-page jumping.

## Consequences

- **Negative:** the frontend cannot offer a numbered pager for the task list — only forward/backward cursor-based paging (infinite scroll or "load more"). If a future admin or reporting view genuinely needs to jump to an arbitrary page of tasks, it will need a separate endpoint or a fallback to offset semantics for that one view.
- **Negative:** cursor pagination is one more pattern for a new engineer to learn, since it differs from every other list endpoint in the same API.
- **Positive:** the task list stays correct — no duplicated or skipped rows — even while a project is under heavy concurrent editing, which is exactly the condition this endpoint is most likely to be under in practice.
- **Positive:** avoids the growing `OFFSET` scan cost in Postgres on the one list that's both hot and deep.

## Consistency Check

Cross-checked against `DESIGN.md` and `api-spec.md`:
- `DESIGN.md` Trade-off 1 states the same decision and criterion as this record.
- `api-spec.md` Section 1 ("Exception: cursor pagination for tasks") uses the identical parameter names (`cursor`, `pageSize`, `status`, `sort`) and response shape (`data`, `nextCursor`, `pageSize`).
- No other document names a different pagination style for the tasks endpoint.
- This record adds one detail not previously written down in either document: the cursor payload's `{sortValue, id}` tie-breaker. That detail is now the authoritative source for it — `DESIGN.md` and `api-spec.md` should be read as deferring to this ADR on the exact cursor encoding.

## Expiry Condition

Revisit this decision if either becomes true:
1. A concrete product requirement emerges for jumping to an arbitrary task-list page (e.g., an admin/reporting dashboard) — at that point, add a parallel offset-based endpoint scoped to that view rather than reversing this decision for the primary list.
2. Measured task-list sizes stay small in practice (e.g., p95 task count per project stays under one page) — if deep pagination never actually happens, the concurrency problem this ADR solves stops mattering, and reverting to offset for API-wide consistency becomes reasonable.
