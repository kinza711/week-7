# ADR-002: Two-Tier Authorization — Guard Pre-Check Plus Authoritative Service Re-Check

**Status:** Accepted
**Date:** 2026-09-04
**Deciders:** Kinza Shahzadi (CMIT Internship, Week 7)

## Why this is a real decision

A single, DRY authorization check in one place (the route guard) is the obviously appealing design — declarative, applied once per route via `@Roles()`, impossible to forget on a new endpoint. That's a real, defensible position, and it's where this design started. It only breaks down once you account for a specific, verifiable fact about the framework: NestJS guards run *before* interceptors in the request lifecycle, so a guard's check cannot be safely enclosed by a transaction that a later interceptor opens. That constraint — not a style preference — is what forces a second look.

## Context

- The API has 20+ endpoints across 5 resources, all requiring role-aware access control.
- A single missed manual authorization check in a service method is a real security hole, and is easy to introduce as new endpoints are added.
- NestJS's documented request lifecycle runs Middleware → Guards → Interceptors (pre) → Pipes → Handler → Interceptors (post). Guards execute before any interceptor, which rules out using an interceptor to open a transaction that a guard's check could run inside of.
- A membership revocation (a role change committed by a different request) can land at any point during another request's processing — the design's stated goal is that a revoked user is rejected on their *very next* request, with no stale window.
- Every protected write already needs a database transaction for the write itself (per `DESIGN.md`'s Concurrency note on task creation).

## Options Considered

**1. Guard-only enforcement**
- *Advantage:* Maximally DRY — one `@Roles()` declaration per route, centrally enforced, nothing for an endpoint author to remember to add manually.
- *Disadvantage:* The guard's membership check runs before any transaction exists. Nothing prevents a revocation from committing in the gap between the guard's read and the later write, so a revoked user could still slip a write through — directly contradicting the immediate-revocation guarantee.

**2. Service-layer-only enforcement (no guard, manual check in every write method)**
- *Advantage:* The check naturally sits inside the same transaction as the write it protects, closing the race window without depending on framework lifecycle ordering at all.
- *Disadvantage:* Must be manually added to every one of 20+ write methods; a single omission is a silent, undetected security hole, and there's no structural guarantee (like a decorator) that a new endpoint won't be shipped without it.

**3. Two-tier: guard as a fast pre-check, Service transaction as the authoritative re-check**
- *Advantage:* Keeps the guard's declarative, hard-to-forget coverage for the common case (reject unauthorized requests early, cheaply, before touching the write path), while the Service's own transactional check — using `SELECT ... FOR SHARE` immediately before the write — is what actually closes the concurrency gap, independent of guard/interceptor ordering.
- *Disadvantage:* Two authorization queries per authorized write instead of one — a small latency cost. It also requires being explicit, in documentation, that the guard is *not* the source of correctness — a subtlety that's easy to get backwards (an earlier draft of this design assumed the opposite).

## Decision

Use **Option 3**: the `RolesGuard` remains on every route as a fast, declarative pre-check (rejecting the common unauthorized case with no database write ever attempted). The **Service's own transactional membership check — not the guard — is authoritative** for correctness: it runs inside the same transaction as the write, using `SELECT ... FOR SHARE`, immediately before the insert.

**Criterion:** correctness under concurrent revocation cannot depend on a framework lifecycle detail (guard-before-interceptor ordering) that wasn't designed to provide transactional guarantees. The extra membership query this costs is negligible against the 500ms write budget stated in Requirement 2 (Non-Functional Requirements).

## Consequences

- **Negative:** every authorized write now performs two membership lookups (guard pre-check, then Service re-check) instead of one — a small, bounded latency cost, not a correctness one.
- **Negative:** this two-tier split must be documented clearly and consistently everywhere the guard is mentioned, or a future engineer may reasonably assume — as an earlier draft of this same design did — that the guard alone is sufficient, silently reintroducing the race.
- **Positive:** the immediate-revocation guarantee holds regardless of how guards, interceptors, or middleware are wired for any given route — the guarantee lives in the Service transaction, not in framework ordering.
- **Positive:** the guard still provides its main practical benefit (cheap, early rejection for the overwhelmingly common unauthorized-request case) without being relied on for anything it structurally cannot guarantee.

## Consistency Check

Cross-checked against `DESIGN.md` and `api-spec.md`:
- `DESIGN.md`'s Trade-off 2 ("Guard contract") and Section 3's "Concurrency note" both describe this same two-tier split — the guard as pre-check, the Service's `SELECT ... FOR SHARE` transaction as authoritative.
- `api-spec.md` doesn't (and shouldn't) describe this internal enforcement mechanism — it's an implementation detail behind the API's stated behavior (`403`/`404` on insufficient role or non-membership), which both documents agree on.
- No document claims the guard alone provides atomicity — that incorrect claim was caught and corrected during review (see `DESIGN.md` revision history) precisely because it contradicted NestJS's actual request lifecycle.

## Expiry Condition

Revisit this decision if NestJS's request lifecycle changes, or the team migrates to a framework where a transaction can be reliably opened *before* the guard/equivalent authorization layer runs (e.g., in middleware that executes ahead of all guards). If that becomes possible, the Service-layer re-check may become redundant, and folding authorization back into a single check point would remove the extra query cost this ADR accepts.
